# Bindings Architecture

This document describes how docprims is consumed from non-Rust languages and how we keep that surface stable.

It is not a release roadmap.

## Principles

- **Thin bindings**: bindings should not re-implement extraction logic; they call FFI and decode JSON.
- **Stable wire format**: all cross-language payloads are schema-conformant v0 `DocprimsExtract` JSON (see `schemas/v0/extract/`).
- **Stable ABI**: the C-ABI is designed to change rarely; contract evolution happens in JSON schema versions.
- **Safe defaults**: resource limits apply equally to file and bytes entrypoints.

## FFI Contract

docprims uses a sysprims-style C-ABI:

- Return an error code.
- Return complex data as a UTF-8 JSON string.
- Provide thread-local error details via `*_last_error*`.
- Caller frees returned strings with `docprims_free_string()`.

Preferred entrypoint for bindings:

- `docprims_extract_bytes_json(data, len, source_uri, options_json, out_json)`

File entrypoint is available but is secondary:

- `docprims_extract_file_json(path, options_json, out_json)`

Key notes:

- `source_uri` is required for bytes extraction and is used for format routing (by extension) and as `source.uri` in the result.
- All returned `char*` are allocated by Rust and must be freed with `docprims_free_string()`.
- Error state is thread-local; callers must read it on the same OS thread that performed the failing call.

## Options JSON

Bindings pass options as JSON to avoid ABI churn.

Current shape (partial overrides allowed):

```json
{
  "limits": {
    "max_input_bytes": 104857600,
    "max_output_bytes": 52428800,
    "max_blocks": 10000
  }
}
```

## Go Bindings

Go is the primary binding for initial consumers.

### API Shape

Bindings should provide a minimal bytes-first API:

- `ExtractBytes(sourceURI string, data []byte, opts *Options) (*DocprimsExtract, error)`
- Optional: `ExtractFile(path string, opts *Options) (*DocprimsExtract, error)`

The Go layer should:

- Call the FFI entrypoint.
- Convert the returned JSON string into a Go struct (or `map[string]any` for a minimal start).
- Convert `DocprimsErrorCode` + `docprims_last_error()` into a Go error type.

### Thread-Local Error Handling

docprims stores error details in thread-local storage (TLS). Go goroutines can move between OS threads between cgo calls.

Go bindings should lock the OS thread for each FFI call that can fail and immediately read+free the error message:

- `runtime.LockOSThread()`
- call FFI
- if error: call `docprims_last_error()` and `docprims_last_error_code()`
- `runtime.UnlockOSThread()`

This matches the sysprims approach and keeps callers from having to manage thread affinity.

### Linking and Artifact Layout

Follow the sysprims pattern:

- `bindings/go/docprims/include/docprims.h` generated by `cbindgen`
- `bindings/go/docprims/lib/<platform>/` contains the FFI library for that target
- Go build tags select platform-specific `#cgo LDFLAGS` files (e.g., `cgo_darwin_arm64.go`, `cgo_windows_amd64.go`).

For local development, allow a `lib/local/<platform>/` override path.

Shared library opt-in:

- Static (default): link from `lib/<platform>/`.
- Shared (opt-in): build with `-tags docprims_shared` and link from `lib-shared/<platform>/`.

**Note:** Shared library mode is only available for glibc targets. Musl targets are static-only.

Runtime search path for `docprims_shared`:

- Linux: `LD_LIBRARY_PATH` must include the `lib-shared/<platform>` directory
- macOS: `DYLD_LIBRARY_PATH` must include the `lib-shared/<platform>` directory
- Windows: `PATH` must include the `lib-shared/windows-amd64` directory

#### Rust static library collisions

Some Go applications may depend on multiple cgo libraries that each vendor a Rust `staticlib`. In that configuration the final
link can fail with duplicate Rust runtime symbols (commonly `_rust_eh_personality`).

docprims does not currently guarantee co-linking with another Rust `staticlib` in the same Go binary.

Recommended mitigations for consumers:

- Gate docprims usage behind a Go build tag until the conflict is resolved.
- Use the `docprims` CLI as a subprocess (no link-time interaction).
- Prefer a shared-library distribution for one of the Rust dependencies.

Musl selection:

- glibc (default): no extra build tags
- musl: `go test -tags musl ./...` (expects `lib/*-musl/`)

### Binary Artifact Policy

docprims follows the sysprims approach for Go:

- The repo may vendor prebuilt static libraries under `bindings/go/docprims/lib/<platform>/`.
- Local developer builds go to `bindings/go/docprims/lib/local/<platform>/` and should not be committed.

If a platform is listed as supported for Go, we should either:

- Vendor the corresponding `.a` library for that platform, or
- Clearly document that the platform requires building the library locally.

## TypeScript Bindings

TypeScript/Node should use a Node-API addon (napi-rs style), mirroring sysprims.

Design goals:

- Load a native addon from `dist/native/`.
- Expose a small API that returns JSON strings and/or parsed objects.
- Keep error mapping explicit and testable.

Implementation notes:

- The addon should call into the C-ABI (docprims-ffi) rather than re-linking all Rust crates.
- Avoid async callbacks in v0; extraction is synchronous by default.

## Windows Notes

- Go/cgo on Windows is expected to use a GNU toolchain (MinGW) and link against a `.a` (not a `.lib`).
- Windows arm64 is currently out of scope for Go bindings due to toolchain constraints; prioritize CLI and TypeScript first.

## Platform Support Policy

docprims tracks sysprims platform direction. For v0.1.x we target a staggered matrix:

- **macOS**: arm64 (drop darwin x64)
- **Windows**: x64 and arm64
- **Linux**: x64 and arm64

Linux note (glibc vs musl): for Go (cgo), we support both glibc and musl variants by shipping
separate prebuilt static libs under distinct platform directories (e.g. `linux-amd64` and
`linux-amd64-musl`). Consumers select musl by building with `-tags musl` (mirrors sysprims).

Go note (Windows arm64): Go/cgo on Windows requires a GNU toolchain (MinGW). MinGW does not currently support
Windows arm64, so Go bindings are expected to support Windows x64 only. Windows arm64 support is targeted for
CLI and TypeScript first; Go may follow later via llvm-mingw or a different distribution strategy.

Platform coverage is validated via CI in stages. If a platform is not covered yet, bindings must fail clearly
(load/link errors should be actionable).

## Testing Strategy

Bindings tests should focus on:

- ABI sanity: `docprims_version()`, `docprims_abi_version()`.
- Successful extraction from bytes for at least one text format and one OOXML fixture.
- Error paths:
  - missing/unknown extension in `source_uri`
  - invalid options JSON
  - limit-triggered partial extraction

Golden JSON equivalence is enforced in Rust. Bindings should validate key fields (`schema_id`, `schema_version`, `source.format.kind`) rather than pinning the entire payload.

## CI Enforcement

To keep bindings and headers from drifting:

- Regenerate `ffi/docprims-ffi/docprims.h` via `cbindgen` in CI and fail if there is a diff.
- Run `go test` using the binding package(s) and ensure the dynamic/static linker can locate the built library.
- If vendoring `.a` libraries, add a CI job that links against the vendored libs (not just `lib/local`).

## Security Notes

- Treat all inputs as untrusted; expose `limits` in bindings.
- Prefer the bytes entrypoint in server contexts to avoid file path confusion.
- Always free returned strings; never call C `free()`.
